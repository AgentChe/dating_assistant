# Сервер Cue

Прокси к Gemini для трёх функций приложения: разбора переписки, первой фразы и коуча. Написан на Go:
[Gin](https://gin-gonic.com) принимает HTTP-запросы, [Genkit](https://genkit.dev/docs/go/backend-frameworks/gin/)
вызывает Gemini. Сервер ничего не хранит: всё нужное приходит в запросе, ответ модели уходит обратно в приложение.
Счётчик бесплатных генераций и подписка — на стороне приложения.

## Как устроен

```
server/
├── main.go          ключ, Genkit, маршруты, запуск и остановка
├── api/             Gin: маршруты, проверка запросов, таймаут, ошибки {"error": {"message"}}
├── flows/           три флоу Genkit: собирают промпт, вызывают модель, приводят ответ в порядок
│   └── prompts/     тексты промптов: shared.md — общие правила Cue, остальные — по задаче
├── model/           запросы и ответы в том виде, в каком их шлёт и читает приложение
└── testdata/        синтетические скриншоты для проверки: переписка, затихшая переписка, анкета
```

Путь запроса: `api` читает JSON и ставит таймаут 45 секунд (приложение ждёт 60) → флоу из `flows` собирает
системный промпт (`prompts/shared.md` + промпт задачи) и сообщение из данных запроса и картинки → Gemini отвечает
JSON по схеме из `model` (Genkit передаёт её модели и проверяет ответ) → флоу поправляет то, что схема не проверит
(подпись под уровнем интереса, сумму долей слов, кавычки вокруг сообщения) → `api` добавляет `id` и отвечает.

## Запуск на Mac

```bash
cp .env.example .env   # и вписать ключ в GEMINI_API_KEY; .env не попадает в git
go run .
```

Сервер слушает `http://localhost:8080`. Приложение ходит в него так:

```bash
flutter run --dart-define=API_BASE_URL=http://localhost:8080
```

На машине команды он работает по адресу `https://cue.192-81-217-92.sslip.io` (см. «Деплой») — его приложение
берёт по умолчанию.

Проверить руками:

```bash
curl -s localhost:8080/api/v1/analyses -d "{\"screenshot\": \"$(base64 -i testdata/chat.jpg)\"}"
```

## Эндпоинты

| Запрос | Ответ | Ошибки |
|---|---|---|
| `POST /api/v1/analyses` `{"screenshot"}` | разбор, как читает `ChatBreakdown.fromJson` | 400 — пустой или не картинка; 422 — на скриншоте не переписка |
| `POST /api/v1/opening-lines` `{"spice", "you"?, "match"?, "profile_screenshot"?, "previous_lines"?}` | `{"id", "line", "match"?}` — `match` только со скриншотом анкеты | 400 |
| `POST /api/v1/coach/messages` `{"text"?, "tone", "spice", "you"?, "messages"?, "chat"?, "breakdown"?, "chat_screenshot"?}` | `{"id", "text", "suggestion"?, "quick_replies", "chat"?}` — `chat` только с новым скриншотом | 400 — пустое сообщение без переписки |
| `GET /healthz` | `ok` — для хостинга | |

Общие ошибки: 413 — запрос больше 15 МБ, 422 — модель отказалась отвечать по правилам безопасности, 503 — Gemini
перегружен или кончилась квота, 504 — модель не ответила за 45 секунд, 502 — остальные сбои модели. Тело ошибки —
`{"error": {"message": "..."}}`, его разбирает `RestApiTransport`.

В логах — только метод, путь, код и время ответа. Скриншоты и тексты переписок туда не пишутся.

## Промпты

`flows/prompts/*.md` — обычный текст, его можно править без знания Go. Промпты вшиваются в бинарник при сборке,
поэтому после правки сервер нужно перезапустить. Описания полей ответа, которые тоже видит модель, — теги
`jsonschema_description` в `model/responses.go`.

## Настройки

| Переменная | Зачем | По умолчанию |
|---|---|---|
| `GEMINI_API_KEY` | ключ Gemini; на хостинге — из секретов | — |
| `GEMINI_MODEL` | модель для всех трёх задач | `googleai/gemini-3.8-flash` |

## Деплой

Сервер работает на машине команды `dev@192.81.217.92` (Ubuntu, nginx, certbot) службой systemd `cue-server`:
слушает только `127.0.0.1:8401`, снаружи до него доходят через nginx и HTTPS. Выкладка — одной командой из папки
`server`:

```bash
./deploy/deploy.sh                          # собрать под Linux, выложить, перезапустить службу
./deploy/deploy.sh --domain api.example.com # то же и сайт nginx с сертификатом Let's Encrypt для домена
```

Что делает скрипт:

- собирает статический бинарник под linux/amd64 и кладёт его в `/opt/cue-server`;
- ставит службу `deploy/cue-server.service`: пользователь `cue` без входа в систему, перезапуск при падении,
  автозапуск после перезагрузки;
- в первый раз берёт `GEMINI_API_KEY` из `server/.env` и кладёт в `/etc/cue-server.env` (права 640, root и группа
  cue); ключ идёт по ssh через stdin и не попадает ни в аргументы команд, ни в логи;
- с `--domain` — сайт nginx из `deploy/nginx-site.conf` (до 16 МБ на запрос, 75 с на ответ) и сертификат через
  `certbot --nginx`. Домен должен уже указывать на 192.81.217.92 (A-запись).

Сейчас сервер работает по адресу `https://cue.192-81-217-92.sslip.io`: sslip.io отвечает на такие имена IP-адресом
из самого имени, а Let's Encrypt выдаёт для них настоящие сертификаты (certbot продлевает сам). Это временно:
приложение зависит от чужого сервиса. Для релиза — свой домен с A-записью на 192.81.217.92, затем
`./deploy/deploy.sh --domain <домен>` и новый адрес в `GlobalDefinitions.apiBaseUrl`.

Логи службы: `sudo journalctl -u cue-server -f`. Другой вариант выкладки — `Dockerfile`: внутри тот же бинарник.
